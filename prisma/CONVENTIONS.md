# Database conventions

Full rules: `CONTEXT/database_schema.md` Section 1 and `CONTEXT/decision_log.md` Decision 12.

## Migration rules

1. **Every schema change is a named migration**, created in development with
   `npm run db:migrate:dev -- --name <snake_case_name>`. Names describe the change
   (`add_assignment_batches`, `leads_add_next_follow_up_date`).
2. **Never edit a migration that has been applied anywhere** (another developer, CI, production).
   Fix forward with a new migration.
3. **Expand / contract.** A migration must work with the previous app version: add columns as
   nullable or with a default; drop or rename only in a later release that no longer uses them.
4. **Raw SQL** for what Prisma cannot express (partial indexes, `CHECK` constraints, triggers) goes
   inside the migration, below the generated SQL, and is listed in `database_schema.md` Section 6.
   Use `--create-only`, add the SQL, then apply.
5. **Drift check.** `npm run db:migrate:check` applies the migrations to the test database and
   diffs it against `schema.prisma`; it fails (exit code 2) when the schema has changes without a
   migration. Raw-SQL indexes and triggers and the `pgboss` schema are not reported as drift.
6. Prisma's automatic seed hook is **not** configured (Decision 11). Seeds run only by their own
   commands.

## Column conventions

- **Instants** (a moment that happened): `DateTime @db.Timestamptz(3)`, stored UTC, named `...At`.
- **Business dates** (a calendar day): `DateTime @db.Date`, handled as `YYYY-MM-DD` strings in
  code, named `...Date`.
- **Time of day:** integer minutes from midnight in the business timezone.
- **Primary keys:** `String @id @default(uuid(7)) @db.Uuid` (UUID v7, generated by Prisma Client).
- **Tables:** `<module>_<plural_noun>` via `@@map`; models are PascalCase with the module prefix.
- **Columns** are named exactly like their Prisma fields (camelCase), so raw SQL double-quotes them.
